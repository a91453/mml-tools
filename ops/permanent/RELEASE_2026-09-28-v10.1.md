## How it was produced

1. **Pin.** The buildId was computed twice from main `a42928a0b386`, each in
   its own clean worktree: once after a fresh `npm ci --ignore-scripts`, as the
   release workflow now runs it, and once with the local dependencies. Both
   gave the same buildId and byte-identical `studio/web-build` trees,
   `verify-studio-artifact.mjs` reported `ARTIFACT_VERIFIED` for both, and
   `package_release.py` produced byte-identical ZIPs and lock from both builds.
   The release workflow switches from `npm install --package-lock=false` to
   `npm ci --ignore-scripts`: this is the first release whose pinned commit
   carries `package-lock.json`, and `tests/dependency-lock-policy.test.mjs`
   no longer exempts the workflow.
2. **Local proof under Bun 1.3** (before publishing).
   - `bootstrap.test.mjs` (5/5, with `RELEASE_TEST_ASSETS=ops/permanent/assets`
     as CI runs it), `publish-release.test.mjs` (7/7) and
     `tests/deployment-topology.test.mjs` (10/10) passed.
   - The rendered function (rendered twice, identical) started offline from a
     cache seeded with the runtime ZIP through the bootstrap's own download
     path: `RENDERED_SOURCE_VERIFIED` → `TRUSTED_SOURCE_VERIFIED` →
     `ARTIFACT_VERIFIED` → `VALIDATED_CACHE_STARTUP` →
     `READY_MARKER_WRITTEN_AFTER_VERIFICATION` → `SERVER_STARTED`. `/health`
     named this buildId, cacheId and source SHA, `/build.json` hashed to the
     lock's `buildJsonSha256`, `/` carried `frame-ancestors 'none'`,
     `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff` and
     `Cache-Control: no-store`, the served `studio/backend/mml/parser.mjs`
     carried the G15 change, and the game-style bank answered 503 with the
     bucket unreachable.
   - A copy with one character changed exited with `RENDERED_SOURCE_MISMATCH`.

## Release steps

1. **Publish.** Run 36406270290 (dispatched on this PR's branch, with
   `origin/main` still at exactly `a42928a0b386`) rebuilt the pinned commit
   and published `studio-v1-durable-a42928a0b386` (`DURABLE_RELEASE_PUBLISHED`).
   The release's runtime ZIP (`sha256:53ee46d2…`, 4,374,172 bytes) and trust
   ZIP (`sha256:28bdb56b…`, 18,984 bytes) carry the lock's pins, and its
   `release-lock.json` is byte-identical to the committed lock (`ff57e94e…`).
2. **Mirror.** Run 36406362591 uploaded both ZIPs to the lock's object keys
   and read each back: `DURABLE_MIRROR_VERIFIED` for the runtime ZIP and the
   trust ZIP. The five `RELEASE_S3_*` repository secrets are still present;
   they are to be deleted (repository Settings → Secrets and variables →
   Actions), which only the owner can do.
3. **Deploy.** The function was deployed before merge, from the rendered file
   (`python ops/permanent/build_function.py ops/permanent/assets <out.ts>`,
   SHA-256 `d52957d2…`, 44,512 bytes), through the Railway API (not Railway
   Agent).
   - **First attempt, failed closed (about 10:00:00–10:02:04 UTC).** The
     source was sent with `staged: true`, but the function source update went
     live at once instead of waiting in the staged changes. The copy sent was
     one blank line short (44,511 bytes, the same fault as v10's first
     staging), so the new deployment exited with `RENDERED_SOURCE_MISMATCH`
     before it touched the cache or started a server, and the domain answered
     502. The v10 deployment was redeployed from its existing build through
     the API and served v10 from cache again (`bootstrap: cache`, buildId
     `55aac2dd…`). No wrong code was served at any time: the self-hash check
     refused the altered copy. The function's stored source was still the
     short copy after the rollback, so the Dashboard's Deploy was not to be
     used until the second attempt replaced it.
   - **Second attempt, 10:52–10:56 UTC.** The source to send was first
     written to a local file and checked against the rendered file (SHA-256
     `d52957d2…`, 44,512 bytes, byte-identical), then sent live. The
     deployment reached `SUCCESS`, and its `RENDERED_SOURCE_VERIFIED` event
     shows that the source it runs hashes to the rendered file. The v10
     deployment became `REMOVED` five seconds after the new server started.
     No staged changes were left behind.
   - For later releases: a function source update does not stay staged, so
     every send is a live deploy. Check the exact bytes (hash and length)
     before sending.

## Rollback

- The previous release's cache stays on the volume, so rollback starts from cache.
- Render the function from the v10 lock (main `37d59cec3762`, the ops files of
  #140's merge, `build_function.py`, SHA-256 `6dd68d1c…`) and replace the
  function source with it, or roll back to the v10 deployment in the
  Dashboard's deployment history. Expect `VALIDATED_CACHE_STARTUP` with
  `refetch: false`.
- Replacing the function source deploys it at once (see Deploy), so check its
  hash and length before sending. Rolling back to the v10 deployment keeps
  v10.1 as the stored function source, so a later Dashboard Deploy would
  start v10.1 again.
