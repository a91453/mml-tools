## How it was produced

1. **Build and publish.** [Release run 35852843517](https://github.com/a91453/mml-tools/actions/runs/35852843517) was dispatched while `origin/main` was exactly the source SHA.
   - CI rebuilt the same buildId, the committed lock was byte-identical (`cmp`), and the run ended with `DURABLE_RELEASE_PUBLISHED`.
2. **Mirror to the bucket.** [Mirror run 35852921168](https://github.com/a91453/mml-tools/actions/runs/35852921168) uploaded both ZIPs to bucket `studio-release-artifacts` at the lock's object keys, then read each back and matched its SHA-256 (`DURABLE_MIRROR_VERIFIED`, `uploaded: true` for both).
3. **Local proof under Bun** (before deploying).
   - Seeding a cache from the local runtime ZIP ran the full chain (`TRUSTED_SOURCE_VERIFIED` → `DURABLE_ZIP_VERIFIED` → `ARTIFACT_VERIFIED` → `ARTIFACT_ATOMICALLY_COMMITTED` → `SERVER_STARTED`), and `/health` reported this buildId and Canonical v2.
   - The rendered function then started from that cache offline: `RENDERED_SOURCE_VERIFIED` → `TRUSTED_SOURCE_VERIFIED` → `ARTIFACT_VERIFIED` → `VALIDATED_CACHE_STARTUP` → `SERVER_STARTED`, with the same `/health`.
   - A copy with one character changed exited with `RENDERED_SOURCE_MISMATCH` before doing anything else.
4. **Deploy.** The function source was replaced with Railway's function-code operation, which created a new deployment from the current configuration; variables, volume, image and healthcheck were unchanged.
   - The deployment passed the `/health` healthcheck and reached `SUCCESS`; the previous deployment (the v1 release) became `REMOVED`.
   - No cache existed for this buildId, so it started from the durable source.
