## How it was produced

1. **Pin.** The buildId was computed twice from main `d7ec3c6ea7bd`, once with the local dependencies and once after a fresh `npm install --ignore-scripts --package-lock=false` as the release workflow runs it. Both gave the same buildId, `verify-studio-artifact.mjs` passed, and `package_release.py` produced byte-identical ZIPs and lock from both builds.
2. **Build and publish.** [Release run 35979205352](https://github.com/a91453/mml-tools/actions/runs/35979205352) was dispatched from the follow-up branch while `origin/main` was exactly the source SHA.
   - CI rebuilt the same buildId, the committed lock was byte-identical (`cmp`), and the run ended with `DURABLE_RELEASE_PUBLISHED`.
3. **Mirror to the bucket.** [Mirror run 35979273252](https://github.com/a91453/mml-tools/actions/runs/35979273252) uploaded both ZIPs to bucket `studio-release-artifacts` at the lock's object keys and read each back (`DURABLE_MIRROR_VERIFIED`, `uploaded: true` for both).
4. **Local proof under Bun** (before deploying).
   - `ops/permanent/bootstrap.test.mjs` and `publish-release.test.mjs` passed against these assets.
   - The rendered function (rendered twice, identical) started offline from a cache seeded with the runtime ZIP: `RENDERED_SOURCE_VERIFIED` → `TRUSTED_SOURCE_VERIFIED` → `ARTIFACT_VERIFIED` → `VALIDATED_CACHE_STARTUP` → `READY_MARKER_WRITTEN_AFTER_VERIFICATION` → `SERVER_STARTED`.
   - `/health` reported this buildId, and pages carried `Content-Security-Policy: frame-ancestors 'none'` and `X-Frame-Options: DENY`.
   - A copy with one character changed exited with `RENDERED_SOURCE_MISMATCH`.
5. **Deploy.**
   - The function source was staged with Railway's function-code operation and read back; its SHA-256 equalled the rendered file.
   - The staged patch held only that change (`Source Code`, 39,762 → 41,250 characters, not destructive).
   - Committing the staged change through the API timed out twice without creating a deployment, as it did for v3, so the owner committed it from the Dashboard.
   - The deployment reached `SUCCESS`; the previous deployment (the v3 release) became `REMOVED`.
   - No cache existed for this buildId, so it started from the durable source.
