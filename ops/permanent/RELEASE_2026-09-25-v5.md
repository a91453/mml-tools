## How it was produced

1. **Pin.** The buildId was computed twice from main `25b8acd2ed21`, once with the local dependencies and once after a fresh `npm install --ignore-scripts --package-lock=false`. Both gave the same buildId, `verify-studio-artifact.mjs` passed, and `package_release.py` produced byte-identical ZIPs and lock from both builds.
2. **Build and publish.** [Release run 36082888877](https://github.com/a91453/mml-tools/actions/runs/36082888877) was dispatched from the pin branch while `origin/main` was exactly the source SHA, and ended with `DURABLE_RELEASE_PUBLISHED`.
3. **Mirror to the bucket.** [Mirror run 36082941278](https://github.com/a91453/mml-tools/actions/runs/36082941278) uploaded both ZIPs to the lock's object keys and read each back.
4. **Local proof under Bun** (before deploying).
   - `bootstrap.test.mjs` (2/2) and `publish-release.test.mjs` (7/7) passed against these assets.
   - The rendered function (rendered twice, identical) started offline from a cache seeded with the runtime ZIP: `RENDERED_SOURCE_VERIFIED` → `TRUSTED_SOURCE_VERIFIED` → `ARTIFACT_VERIFIED` → `VALIDATED_CACHE_STARTUP` → `READY_MARKER_WRITTEN_AFTER_VERIFICATION` → `SERVER_STARTED`, with `/health` naming this buildId and pages sent with `frame-ancestors 'none'` and `X-Frame-Options: DENY`.
   - A copy with one character changed exited with `RENDERED_SOURCE_MISMATCH`.
5. **Deploy.** The function source was staged and read back (its SHA-256 equalled the rendered file). Committing through the API timed out, as for v3 and v4, so the owner committed it from the Dashboard. The deployment reached `SUCCESS`; the v4 deployment became `REMOVED`.
