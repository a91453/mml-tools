## How it was produced

1. **Pin.** The buildId was computed twice from main `37d59cec3762`, each in
   its own clean worktree: once after a fresh `npm install --ignore-scripts
   --package-lock=false`, as the release workflow runs it, and once with the
   local dependencies. Both gave the same buildId, `verify-studio-artifact.mjs`
   reported `ARTIFACT_VERIFIED` for both, and `package_release.py` produced
   byte-identical ZIPs and lock from both builds.
2. **Local proof under Bun 1.3** (before publishing).
   - `bootstrap.test.mjs` (5/5, with `RELEASE_TEST_ASSETS=ops/permanent/assets`
     as CI runs it), `publish-release.test.mjs` (7/7) and
     `tests/deployment-topology.test.mjs` (10/10) passed.
   - The rendered function (rendered twice, identical) started offline from a
     cache seeded with the runtime ZIP: `RENDERED_SOURCE_VERIFIED` →
     `TRUSTED_SOURCE_VERIFIED` → `ARTIFACT_VERIFIED` → `VALIDATED_CACHE_STARTUP`
     → `READY_MARKER_WRITTEN_AFTER_VERIFICATION` → `SERVER_STARTED`. `/health`
     and `/build.json` named this buildId and source SHA, pages carried
     `frame-ancestors 'none'` and `X-Frame-Options: DENY`, the served
     `index.html` carried #139's nine-stage navigation and the served
     Workshop guide stylesheet #138's folded boxes, and the game-style bank
     answered 503 with the bucket unreachable.
   - A copy with one character changed exited with `RENDERED_SOURCE_MISMATCH`.

## Release steps

1. **Publish.** Run 36368653006 rebuilt `37d59cec3762` with
   `origin/main` at exactly that commit, reported `ARTIFACT_VERIFIED`, matched
   the committed lock byte for byte and published
   `studio-v1-durable-37d59cec3762` (`DURABLE_RELEASE_PUBLISHED`; runtime ZIP
   `sha256:331ffef0…`, trust ZIP `sha256:28bdb56b…`, the lock's pins).
2. **Mirror.** Run 36368688914 uploaded both ZIPs to the lock's
   object keys and read each back: `DURABLE_MIRROR_VERIFIED` for the runtime
   ZIP (4,370,597 bytes) and the trust ZIP (18,984 bytes). The five
   `RELEASE_S3_*` repository secrets were still present from an earlier
   release; they are to be deleted (repository Settings → Secrets and
   variables → Actions), which only the owner can do.
3. **Merge.** The pin PR merged as #140 (main `4b04edd6c173`).
4. **Deploy.** The rendered function (`python ops/permanent/build_function.py
   ops/permanent/assets <out.ts>`, SHA-256 `6dd68d1c…`) was staged through the
   Railway API (not Railway Agent) and read back. The first staging came back
   one byte short (a blank line dropped when the source was passed to the
   API) and was replaced before anything was committed; the second read back byte-identical. The staged
   patch changed only the source code and was not destructive. Committing it
   through the API timed out twice without applying it (the patch stayed
   `STAGED`, as with v9), so the owner committed it from the Dashboard. The
   deployment reached `SUCCESS`, the v9 deployment became `REMOVED`, and the
   deployed function source reads back byte-identical to the rendered file.
